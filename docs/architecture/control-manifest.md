## Foundation Layer Rules

*Applies to: module layout, the deterministic sim core, the PRNG module, backend
stack, database schema, commit protocol, engine start-up*

### Required Patterns

- **Code root is `src/` (Vite app at the repo root, pnpm)**; backend in `server/`;
  question banks in `content/banks/<module>/<round-type>.json` with
  `content/version.json` holding the current global version — source: ADR-0004 §1
- **Import rules (lint-enforced)**: `src/game/**` imports nothing from `src/ui`,
  `src/net`, `react`, `react-dom`, DOM/browser globals, `fetch` or storage — it is
  host-agnostic pure TS. `server/**` imports `src/game/**` freely; never `src/ui/**`
  or `src/net/**`. `src/net/**` may import `src/game/**` *types* only; never runs
  game math. `src/ui/**` may import `src/game/**` and `src/net/**`; nothing imports
  `src/ui` except `src/ui` and the entry. `content/**` is imported by no bundle —
  source: ADR-0004 §1
- **B1–B12 and every F-series formula live exactly once in `src/game/formulas/`**
  as pure functions with explicit inputs; no ambient state, no clocks read inside
  formulas — time enters as a parameter — source: ADR-0004 §2
- **Gameplay constants live in `src/game/constants/` as frozen typed records, one
  module per owning GDD**, every value commented with its GDD row; data-driven
  values (e.g. `classes.json`) are loaded at runtime so a value edit needs no code
  change — source: ADR-0004 §2 (coding standard: data-driven, never hardcoded)
- **The round engine exposes `resolve_round(profile, mode, seed, round_index,
  input_source)`** with the opponent as a `RoundInputSource` parameter
  (ghost profile / live-commit stream) — never a conditional scattered through
  round logic — source: ADR-0004 §3
- **Published questions are soft-deleted only**; superseded content stays queryable
  across versions — source: ADR-0004 §4
- **`raw-data/` is frozen read-only reference**: never imported by `src/` or
  `server/`, excluded from builds and lint scope; not deleted or relocated without
  an explicit user decision — source: ADR-0004 §5
- **Seeded RNG is splitmix64, pinned as specified**: `GAMMA = 0x9E3779B97F4A7C15`,
  `MIX1 = 0xBF58476D1CE4E5B9`, `MIX2 = 0x94D049BB133111EB`, 64-bit arithmetic as
  32-bit halves with `Math.imul` and unsigned shifts; uniform integers take the
  **top 53 bits** (`draw53 = hi × 2²¹ + (lo >>> 11)`) — source: ADR-0001 Decision
- **Child streams derive via `childStream(seed, tag)`**: FNV-1a 64 fingerprint of a
  module-owned tag constant, `state₀ = mix(battleSeed ⊕ fingerprint(tag))`; tags
  are an open, append-only set — source: ADR-0001 Decision
- **The battle seed is one uint64 from `crypto.getRandomValues` per battle**,
  persisted in the battle record (`seed_hi INT, seed_lo INT` — two columns; uint64
  does not fit Postgres int8) — source: ADR-0001 Decision; ADR-0002 Decision
- **Vector fixtures are generated by the implementing story and cross-checked
  against a published independent splitmix64 implementation; a vector failure is a
  build failure** — never hand-written 64-bit vector literals — source: ADR-0001
  Decision (Vector policy)
- **Backend: Node.js (current LTS) + TypeScript + Fastify, one stateless HTTP API
  service**; JSON-Schema structure validation on commits; storage is a single
  managed PostgreSQL instance accessed provider-agnostically through a connection
  string (thin query layer, no ORM at MVP) — source: ADR-0002 Decision
- **Schema contract**: `commits(commit_id PK, …)` unique — a replayed ID answers
  with the recorded original result; every per-account table FKs to `accounts ON
  DELETE CASCADE`; consumable guards are conditional `UPDATE … WHERE not_consumed`
  inside the commit transaction — source: ADR-0002 Decision
- **Schema freeze policy: additive, nullable, backward-compatible migrations only**
  — post-freeze changes must not rewrite or drop existing columns — source:
  ADR-0002 Decision
- **Sessions: opaque 256-bit crypto-random tokens, stored SHA-256-hashed
  server-side, delivered as `httpOnly; Secure; SameSite=Lax` cookies**; validity is
  `now − last_active_at < TTL_idle` against the **server clock** with strict `<`;
  unlimited concurrent sessions at MVP — source: ADR-0002 Decision
- **Password hashing: argon2id, m=19456 KiB, t=2, p=1** (re-verify against current
  OWASP guidance at implementation); 128-char input bound kept as-written —
  source: ADR-0002 Decision
- **Content delivery is version-keyed API + client-side browser-storage cache**
  (`GET /api/content/version` on every app load; `GET /api/content` only on
  mismatch); no CDN at MVP — source: ADR-0002 Decision
- **Email goes through a thin `Mailer` port** (verify + reset + future mail);
  provider chosen at deployment, verified for Vietnamese-inbox deliverability
  before public testing — source: ADR-0002 Decision
- **QA delay-override profiles are client build config only** — data-driven
  constants in the sim core, swapped at build time — source: ADR-0002 Decision
  (OQ-FS1)
- **Every commit-point system speaks the ADR-0003 commit envelope**: client-generated
  `commit_id`, JSON-Schema-validated payload, atomic apply-or-reject, `applied |
  replayed | rejected` responses with `state_digest`; idempotency anchor is
  **seed** for `battle_end`/`tower_stage_result`, **commit_id** for all other
  types — source: ADR-0003 §1
- **Battle-start registration for every battle from MVP** (telemetry; never blocks
  the commit path); enforced on ranked commits at Stage 1 — source: ADR-0003 §2
- **Stage-1 ranked verification is replay through the shared module imported
  verbatim** ("one formula module, two hosts"); never a parallel outcome
  computation — source: ADR-0003 §3
- **Boundary lint rules and the dual-context vector CI job (client build context +
  server import context) are planted in the same change as the skeleton and
  watched failing once** (planted violation → red → remove) — source: ADR-0004 §2,
  Implementation Guidelines

### Forbidden Approaches

- **Never use `Math.random` anywhere in game math** — it is unseedable; breaks the
  seed-only replay contract — source: ADR-0001 (Alternatives 3; Implementation
  Guidelines)
- **Never use BigInt in the PRNG module, or floats in state evolution** — state
  travels as `[hi, lo]` or hex — source: ADR-0001 Decision
- **Never interleave streams, share one stream across domains, re-seed mid-battle,
  or re-draw a resolved round** — source: ADR-0001 Implementation Guidelines
- **Never hand-write 64-bit vector literals into tests** without
  cross-implementation confirmation — source: ADR-0001 Implementation Guidelines
- **Never fork the formula/PRNG module server-side** ("port" it to the server
  codebase) — two truths for the game's core math, discovered by balance anomaly
  instead of CI — source: ADR-0004 Alternatives 2
- **Never adopt a pnpm workspace monorepo** (apps/web + apps/server +
  packages/game-core) — more moving parts against the pinned tooling's grain;
  revisit only if a third host appears — source: ADR-0004 Alternatives 1
- **Never import or bundle `content/` into the client** — the client fetches
  content at runtime (AC-D1); the server reads it only in the publish path —
  source: ADR-0004 Alternatives 3, §1
- **Never use a BaaS platform as the architecture** (Supabase/Firebase as the
  backend); managed Postgres *as a component* is fine — the commit model is the
  system's core and is owned as ordinary code — source: ADR-0002 Alternatives 1
- **Never use stateless JWT sessions** — revocation (AC-A6/A7) would need a
  server-side denylist anyway — source: ADR-0002 Alternatives 2
- **Never use bcrypt** — hard 72-byte ceiling would force silent truncation or a
  GDD rewrite — source: ADR-0002 Alternatives 3
- **Never partially apply a commit, or re-apply a seen commit ID / seed anchor** —
  source: ADR-0003 Implementation Guidelines
- **Never use server-side recompute that does not reuse the battle engine** — it is
  either a drift risk or replay with less coverage — source: ADR-0003 Alternatives 1
- **Never use signed client attestations** (HMAC with an embedded secret) — any
  browser-bundle secret is extractable; security theater against a modified client —
  source: ADR-0003 Alternatives 2
- **Never let the forfeit window be extended by client events** — the flat T+15
  window from `started_at` is the assertable contract — source: ADR-0003
  Alternatives 3, §4
- **Never consult a client-supplied timestamp for session validity**; never log or
  persist raw session tokens — source: ADR-0002 Implementation Guidelines
- **Never truncate an over-bound password** — reject it with a clear message —
  source: ADR-0002 Implementation Guidelines (Edge Case 6)
- **Never return a registration/reset response that differs for existing vs
  non-existing accounts** — byte-identical generic responses — source: ADR-0002
  Implementation Guidelines (AC-A5/A8)
- **Never orphan progress rows on account deletion** — every per-account table
  FK-cascades — source: ADR-0002 Implementation Guidelines
- **Never let a telemetry failure block the MVP commit path** — source: ADR-0003
  Implementation Guidelines
- **Never put gameplay values in source code, read a clock inside a formula,
  restate a shared constant locally, or branch on encounter kind inside battle
  logic** — source: ADR-0004 Implementation Guidelines
- **Never hard-delete published questions** — soft-delete only — source: ADR-0004
  Implementation Guidelines

### Performance Guardrails

- **PRNG**: negligible — ≤ ~20 draws/battle, each O(1) (~4 `imul`s); one
  `[hi, lo]` pair per live stream; streams are per-battle ephemeral — source:
  ADR-0001 Performance Implications
- **Auth**: argon2id ~19 MiB × t=2 per login verify, bounded by in-memory login
  throttling (throttle counters deliberately not persisted; restart clears them —
  accepted) — source: ADR-0002 Performance Implications
- **Commits**: one commit per commit-point action — at most five calls per battle
  session; content payload fetched only on version mismatch — source: ADR-0002
  Performance Implications
- **Warm app load never waits on the network for cached content** — one cheap
  version check — source: ADR-0002 Performance Implications
- **Stage-1 ranked replay**: one sub-millisecond-scale sim per ranked commit;
  forfeit scan one query per minute — source: ADR-0003 Performance Implications
- **Battle-start registration**: one insert at battle start, off the critical
  render path (fire-before-first-round) — source: ADR-0003 Performance
  Implications

## Core Layer Rules

*Applies to: core gameplay loop, battle system, opponent AI, question resolution*

### Required Patterns

- **All game math draws from `src/game/prng.ts` — the project's only seeded random
  source** (`RngStream`, `childStream`, `hashH`) — source: ADR-0001 Key Interfaces
- **Draw exactly once per ghost round, in strict round order**;
  `ghost_correct = draw53 < threshold` where
  `threshold = round_half_up(accuracy × 2⁵³)` — equality is NOT correct — source:
  ADR-0001 Decision (Architecture Diagram)
- **The crit fast path (elapsed < 3000 ms) draws nothing**; wrong answers and
  timeouts draw nothing — source: ADR-0001 Implementation Guidelines
- **Naive modulo is blessed for ranges r ≤ 501** (`rngInt(lo, hi)`); any range
  > 2³² must use rejection sampling — source: ADR-0001 Decision
- **Callers never convert draws to float for gameplay comparison** — the runtime
  domain is fixed-point integers on [0, 2⁵³) — source: ADR-0001 Key Interfaces
- **The opponent is injected as `RoundInputSource`** — MVP ghost profile draws from
  `(seed, "ghost")`; the battle engine never branches on "am I PvP" — source:
  ADR-0004 §3
- **Replay needs only the seed** — the replay record stores the seed, not draws —
  source: ADR-0001 Decision (child-stream consequences)

### Forbidden Approaches

- **Never use `Math.random` in game math** (platform RNG is allowed only in client
  networking, e.g. retry jitter — outside the sim core) — source: ADR-0001
  Implementation Guidelines; ADR-0003 §5
- **Never interleave, share, re-seed, or re-draw streams** (see Foundation) —
  source: ADR-0001 Implementation Guidelines
- **Never put speech-io's scorer or forge's filler draw inside the seeded
  streams** — scorer uses platform RNG, forge filler is DI-injected, per their
  GDDs — source: ADR-0001 Implementation Guidelines
- **Never hand-write 64-bit vector literals without cross-implementation
  confirmation** — source: ADR-0001 Implementation Guidelines
- **Never re-derive a resolved round's outcome** (fixed-point domain only) —
  source: ADR-0001 Key Interfaces

### Performance Guardrails

- ≤ ~20 seeded draws per battle, O(1) each — source: ADR-0001 Performance
  Implications

## Feature Layer Rules

*Applies to: ranked league, forge, equipment, tower, quests, meta-progression*

### Required Patterns

- **Every commit-point action goes through the ADR-0003 commit envelope** with its
  type's idempotency anchor (seed for battle/tower results, commit_id for forge
  resolution, stone application, equip change, quest claim) — source: ADR-0003 §1
- **Ranked RP verification (Stage 1)**: ranked `battle_end` carries `answer_log`;
  the server replays through the shared module and applies the RP delta
  (±28/−14, RL2 floored at 0) server-side on agreement — source: ADR-0003 §3
- **Ranked `H` is the stateless single draw** `hashH(x)` —
  `state₀ = mix(x ⊕ fingerprint("ranked-peer"))`;
  `rng_int(seed, lo, hi) = lo + (H(seed) mod (hi − lo + 1))` — source: ADR-0001
  Decision
- **Ranked forfeit**: `ranked_forfeit_grace_min` = 15 measured from `started_at`
  (server clock); exactly one forfeit, RP −14 floored at 0, second expiry writes
  nothing; late result rejected whole (first resolution wins); reconnect inside
  the window applies normally — source: ADR-0003 §4
- **New draw kinds are append-only named positions** (F2 rule 7): a domain tag is
  immutable once shipped — source: ADR-0001 Implementation Guidelines
- **Client commit state machine**: `idle → committing → applied|replayed → idle`;
  F3 auto-retries (n < 5, platform-RNG jitter), then Unsaved-state (commit kept in
  memory, blocked actions, `beforeunload` warning); manual and post-re-login
  retries restart the ladder at n = 0 — source: ADR-0003 §5

### Forbidden Approaches

- **Never require `answer_log` of friend/tower commits** — ranked only — source:
  ADR-0003 Implementation Guidelines
- **Never let a late result overwrite a forfeit, or let the forfeit machinery
  touch non-ranked battles** — friend/tower abandons are silently discarded —
  source: ADR-0003 §4, Implementation Guidelines
- **Never persist unsaved commits to browser storage** — they live in memory
  (AC-C6) — source: ADR-0003 §5
- **Never ship QA delay-override profiles as production defaults or encode them in
  the persistence schema** — build config only — source: ADR-0002 Implementation
  Guidelines
- **Never apply event-extension to the forfeit grace window** — source: ADR-0003
  Alternatives 3

## Presentation Layer Rules

*Applies to: React UI, screens, HUD, result modals, client networking UI*

### Required Patterns

- **`src/ui/**` is React-only Presentation** — it may import `src/game/**` and
  `src/net/**`, and nothing else imports it — source: ADR-0004 §1
- **Present every commit state**: committing, applied, replayed, failed →
  Unsaved-state banner "Lưu không thành công — Thử lại", commit-requiring actions
  blocked (same blocked set as offline), `beforeunload` warning — source: ADR-0003
  §5
- **Ranked result modal flags a forfeited battle** (`forfeit` flag from ADR-0003
  §4); ranked UI MAY warn `beforeunload` during ranked battles — source: ADR-0003
  §4
- **Content is re-read only at full app load** — a session never switches content
  mid-battle (AC-E5); warm loads come from the version-keyed browser-storage cache
  — source: ADR-0002 Decision
- **Retry jitter uses the platform RNG** — client networking is outside the seeded
  streams by ADR-0001's own scope note — source: ADR-0003 §5

### Forbidden Approaches

- **Never persist game state to browser storage** except the session cookie and
  the version-keyed content cache (AC-C6) — source: ADR-0002 Implementation
  Guidelines
- **Never persist unsaved commits to browser storage** — memory only — source:
  ADR-0003 §5
- **Never switch a session's content mid-battle** — source: ADR-0002 Decision
  (AC-E5)

### Cross-Cutting Constraints

- **The seed is the battle identity end-to-end**: registration key, commit anchor,
  replay input — source: ADR-0003 §2
- **"One formula module, two hosts"**: every formula and stream is written once in
  `src/game/` and imported verbatim by both client and server; drift between hosts
  is a build failure, proven by dual-context CI and the cross-host replay identity
  test — source: ADR-0001 (PRNG guideline); ADR-0004 §2; ADR-0003 §3
- **The persistence schema is the contract** (no ORM magic, no computed-on-read:
  `due_at`, `seed_hi/seed_lo`, `commit_id` stay plain data) — source: ADR-0002
  Implementation Guidelines
- **Client trust: browser storage holds only the session cookie and the
  version-keyed content cache**; everything else lives server-side — source:
  ADR-0002 (AC-C6)
- **Gameplay values are data-driven** — constants module or JSON data file, never
  hardcoded — source: ADR-0004 Implementation Guidelines (coding standard)
- **Verify before recording: Stage-1 ranked outcomes are derived, not
  reported** — every trust-model escalation reuses the shared deterministic module —
  source: ADR-0003 §3
